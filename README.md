# dsh-chrome-mcp

[Chrome DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp)
for [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (dsh)
0.2: launches `chrome-devtools-mcp` as an MCP server over stdio
(`npx -y chrome-devtools-mcp@latest [extraFlags]`) through the stock
`@deepseek-ai/dsh-mcp-client` bridge, so the agent gets the full Chrome
inspection tool set (`mcp__chrome__*` tools).

Written for the dsh 0.2 settings model: **there is no custom browser code.**
The Settings → Plugins page is generated by the harness from the plugin's own
config schema, and the two fields that matter day to day — **Extra flags**
and **Chrome executable** — are marked *volatile*, so editing them in the
GUI is committed to the running process, relaunches the bridge, and re-runs
the Chrome executable check — no dsh restart.

## Install

Add the package as a dependency of the profile you run (e.g. the web GUI
profile at `~/.dsh/profiles/web/package.json`):

```sh
cd ~/.dsh/profiles/web
pnpm add dsh-chrome-mcp
```

The package ships its own composition patch (`cordis.patch.yml`), so the
`chrome-mcp` host entry is inserted automatically and appears under
**Settings → Plugins → chrome-mcp**. Restart dsh to pick up the new entry.

If you previously used `@comecaramelos/dsh-chrome-mcp`: remove that package
(it targets the pre-0.2 API and cannot activate on dsh 0.2) before adding
this one.

## Configuration

Everything below is ordinary dsh row config for the `chrome-mcp` entry;
fields marked *editable in Settings* live on the GUI page.

| Field | Default | Editable in Settings | Meaning |
| --- | --- | --- | --- |
| `extraFlags` | `["--no-usage-statistics", "--no-performance-crux"]` | yes | Flags appended after the npm spec, e.g. `--headless`, `--isolated`. Control characters and empty entries are rejected by the schema, so the GUI refuses them at save time. |
| `chromePath` | `""` (discover) | yes | Chrome executable passed to the bridge as `--executablePath=<path>` (unless a flag already pins one). |
| `serverName` | `chrome` | no | Tool namespace: tools register as `mcp__<serverName>__<tool>`. |
| `command` | `npx` | no | Launcher executable. |
| `package` | `chrome-devtools-mcp@latest` | no | npm spec handed to the launcher. |
| `chromePaths` | per-platform stable-channel locations | no | Discovery candidates when `chromePath` is empty. |
| `env` | `{}` | no | Extra environment for the bridge process. |
| `cwd` | `""` | no | Working directory for the bridge process. |
| `toolCallTimeoutMs` | `60000` | no | Timeout for one MCP tool call. |
| `failOnStartupError` | `false` | no | Fail the plugin when the bridge cannot start, instead of logging and letting the reconnect policy retry. |
| `reconnect` | enabled, 500ms → 30s, 10 attempts | no | Reconnect policy passed through to the MCP bridge. |

Fields marked *no* are changed in the profile patch
(`~/.dsh/profiles/web/cordis.patch.yml`) under the `chrome-mcp` entry:

```yaml
- id: chrome-mcp
  config:
    serverName: chrome
    extraFlags:
      - --headless
      - --isolated
```

### Flags precedence

1. `extraFlags` explicitly set in the row config (or saved from Settings).
2. `DSH_CHROME_MCP_FLAGS` in the launch environment — a whitespace-separated
   list, e.g. `DSH_CHROME_MCP_FLAGS="--headless --isolated"` — honored only
   while the config still holds the schema default, for one-off launches.
3. The schema default.

## Status reporting

dsh 0.2 gives module plugins no push channel to the browser, so status is
log-based (host log, `dsh` stderr):

* At mount (and after every Settings edit) the plugin probes Chrome:
  `chrome-mcp(chrome): Chrome check passed: Google Chrome 140.0.0.0` or
  `chrome-mcp(chrome): Chrome check failed: <first error line>` — the
  known *"no Chrome executable detected"* failure additionally cites the
  [configuration guide](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/configuration.md).
* Failed chrome tool calls are summarized as warnings
  (`navigate_page failed: Target closed`); a later successful call logs
  `chrome tools responding again`. Bridge connection problems (reconnect
  backoff, spawn failures) come from the MCP client's own log lines.

A quick probe without starting dsh:

```sh
node scripts/verify-check.mjs
```

## WSL

From WSL the executable must be a **Linux** binary. Launching the Windows
`chrome.exe` through the WSL interop layer fails: `chrome-devtools-mcp`
connects with `pipe: true` (inherited fds 3/4), which Windows-side processes
cannot receive, and its WebSocket fallback hard-codes `127.0.0.1` in the
`DevToolsActivePort` file, unreachable across the WSL2 NAT bridge. The
default discovery list therefore never points at `/mnt/c/...`.

## Development

```sh
pnpm install
pnpm run check   # typecheck + vitest
pnpm run build   # lib/ (ESM + types)
```

`test/mount.spec.ts` mounts the plugin over a mocked MCP client and asserts
the bridge argv, including that a config update relaunches it with the new
flags. The pure modules (schema, discovery, argv, env precedence, tool-note
projection) carry the rest.
